## What we're building & why

MP-06 creates a complete, validated, persisted corpus of ordered positions extracted from the captured games, so later milestones can retrieve positions and traverse games without re-deriving them. Extraction reads the normalized games from `data/database/chess_games.db`, replays every accepted game (ply zero plus one ordered position after every half-move), stores each position losslessly (six-field FEN kept as independently usable fields), and maintains a deduplicated first-four-field position-state index with occurrence counters kept separate. The corpus is identified by the subject player's stable UUID (Skyrocoster, `0101b08a-ce8b-11ee-b2fd-e90263e5548c`), game membership is `rules=chess` with the subject appearing exactly once, and publication is atomic: new corpus state is visible only after the whole run and its completeness checks pass, and a failed or interrupted run rolls back so readers keep the previous complete corpus.

The milestone is staged into four separately-judgeable human-visible shipments so no stage is a giant undifferentiated blob: first the dependency plus the extraction-owned schema are created and human-accepted before any position data, then the replay/persistence engine is proven on small temporary fixtures (standard, custom-start, shortened-final-FEN, and non-capturable en-passant) before touching the full real corpus, then the full corpus is populated with live progress, run history, publication checks and atomic publish for human acceptance, and finally incremental new/changed/removed/no-change reruns plus failure, interruption and concurrent-writer recovery are proven. Fetching and extraction remain separate explicit commands; MP-06 adds no backend or frontend corpus API.

## Data contract (confirmed by the grilling record)

Extraction-owned, versioned corpus tables are added to `data/database/chess_games.db`. The fetcher owns `games`, `players`, and `fetch_state` and never writes corpus tables; extraction reads those source tables read-only and never writes them. Ordered positions are **game-global** (not per-corpus): `corpus_game` owns membership, and removing one corpus's membership preserves a game's occurrences while any corpus still references that game. A `position_state` row is removed only when no occurrence references it. The schema uses conservative defaults: integer surrogate IDs where useful, the stable subject UUID as corpus identity, normalized first-four-field position state, occurrence counters kept separate, one transaction per corpus publication, and no speculative temp/work artifacts (SQLite's own journaling suffices).

- `corpus` — `corpus_id` INTEGER PK, `subject_player_uuid` TEXT NOT NULL UNIQUE REFERENCES `players(uuid)`.
- `corpus_game` (membership + change detection) — `corpus_id` FK, `game_uuid` FK to `games(uuid)`, `rules` TEXT NOT NULL (must be `chess`), `fingerprint` TEXT NOT NULL; PK `(corpus_id, game_uuid)`.
- `position_state` (unique four-field state, game-global) — `state_id` INTEGER PK, `placement` TEXT, `side_to_move` TEXT, `castling` TEXT, `en_passant` TEXT; UNIQUE `(placement, side_to_move, castling, en_passant)`.
- `position_occurrence` (per game per ply, game-global) — `occurrence_id` INTEGER PK, `game_uuid` FK to `games(uuid)`, `ply` INTEGER NOT NULL, `state_id` FK to `position_state`, `san` TEXT NULL (NULL at ply 0), `uci` TEXT NULL (NULL at ply 0), `halfmove_clock` INTEGER NOT NULL, `fullmove_number` INTEGER NOT NULL; UNIQUE `(game_uuid, ply)`, INDEX `(state_id)`.
- `corpus_schema` (true singleton) — `id` INTEGER PRIMARY KEY CHECK (`id = 1`), `version` INTEGER NOT NULL, `applied_at` TEXT NOT NULL. Init creates the tables and sets version 1; any existing corpus schema with version != 1 is refused with a clear error and no writes (no auto-migration in MP-06).
- `corpus_run` (run history, separate from the atomic corpus data) — `run_id` INTEGER PK, `corpus_id` FK, `status` TEXT NOT NULL (`running`/`success`/`failed`/`interrupted`), `started_at` TEXT, `finished_at` TEXT NULL, `accepted_games`, `excluded_games`, `new_games`, `changed_games`, `removed_games`, `unchanged_games`, `ordered_positions`, `unique_states` INTEGER NOT NULL, `validation` TEXT NOT NULL (concise summary), `details` TEXT NULL (concise failure text).

The subject's color derives from each game's white and black player UUIDs. The unique-state index groups the first four FEN fields; halfmove and fullmove counters stay on each occurrence, so a complete six-field FEN reconstructs from the join. This shared index is not a promise that engine analysis is reusable between occurrences (that is MP-09).
