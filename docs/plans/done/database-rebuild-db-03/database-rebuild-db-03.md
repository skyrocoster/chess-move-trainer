## Outcome

Provide a clean, package-owned, two-stage DB-03 toolchain that uses the Chess.com archive response transiently to discover listed months, safely acquires and retains raw Chess.com month data, then independently normalizes accepted standard trainer games into `datasource_game`, `derived_game_position`, and shared permanent `derived_position` rows. Month-file publication and each accepted game's database correction are atomic at their separate boundaries, so a structurally incomplete month response, invalid normalized game, or interruption cannot damage the last usable raw month or a previously valid normalized game. DB-03 adds no schema table and does not authorize implementation merely because this Plan exists.

## Scope

- **Included:** From-scratch ownership under `chess_move_trainer.database.games`; package configuration; synchronous HTTP archive discovery and month acquisition; raw month validation and atomic storage; pure game normalization and PGN replay; trainer-oriented metadata; per-valid-game persistence and correction; opaque composition with DB-02 canonical positions; thin Typer commands; synthetic fixtures and focused package/CLI proof.
- **Expected areas:** `src/chess_move_trainer/database/games/__init__.py`, `configuration.py`, `acquisition.py`, `raw_storage.py`, `normalization.py`, and `persistence.py`; `src/chess_move_trainer/database/cli.py`; package exports only where they are intentionally public; a narrowly bounded adjustment to `src/chess_move_trainer/database/connection.py` and/or `src/chess_move_trainer/database/positions/repository.py` only if opaque same-transaction composition requires it; `tests/database/games/` and its synthetic fixtures; focused additions to `tests/database/test_package_boundary.py`, `tests/database/test_source_boundary.py`, `tests/database/test_position_transactions.py`, or `tests/database/test_cli.py` only when their existing cross-package contract is affected.
- **Existing substrate:** DB-01/DB-02 continue to own the exact schema, configured SQLite connections, canonical legal-only position identity, and permanent position repository. DB-03 uses the existing `datasource_game`, `derived_position`, and `derived_game_position` DDL in `schema_v1.sql`; it does not change DDL.
- **Public CLI:** Extend `python -m chess_move_trainer.database` with Typer group `games` and supported commands `games acquire --config PATH --raw-root PATH` plus `--username`, `--trainer-chesscom-uuid`, `--request-timeout 30.0`, and `--request-delay 0.25`; and `games import --config PATH --raw-root PATH --database PATH` plus `--trainer-chesscom-uuid`. The explicit paths are required. YAML owns separate `username` and `trainer_chesscom_uuid` values; an explicit CLI value overrides its matching YAML value, and neither identity is derived or profile-fetched. Optional YAML `request_timeout` and `request_delay` values use the same meanings and are overridden by explicit CLI values. Timeout seconds must be finite and positive; delay seconds must be finite and nonnegative. Production always uses the fixed Chess.com API endpoint; no public base-URL option exists, while transport remains injectable below the CLI for tests.
- **CLI contract:** Commands are thin, noninteractive, and automation-safe, print useful `--help`, and report diagnostics without persisting run/failure state. Exit `0` means completed, including reported normalization skips; `1` means incomplete or operational failure; `2` means invalid Typer invocation or invalid configuration; `130` means user interruption, with the active game rolled back or active raw publication left unpublished. Rate limiting is an ordinary operational failure under `1`, with no special state or exit code.
- **Separation:** Acquisition performs transient archive discovery and persisted raw-month-file work only and never opens SQLite. Import reads local raw month files and writes the explicit database only and never accesses the network. Shared services, not CLI adapters, own behavior.
- **Raw layout and acquisition:** Only `games/YYYY/MM.json` month files are DB-03's persisted ledger and publication targets; each month envelope contains a top-level `games` list. The network archive response is validated and used transiently to discover listed month URLs, then discarded. Any pre-existing `archives/<username>.json` is read-only raw evidence and must not be created, replaced, or otherwise modified by DB-03. “Current” is the UTC calendar month and is eligible only when that exact month is listed by Chess.com. Never construct/request an unlisted current-month URL and never substitute the latest historical month. Existing historical month files are immutable ledger entries and are skipped; a listed missing historical month is requested once, validated, atomically created, then immutable. No raw source is deleted.
- **Raw safety and completeness gate:** A month response is structurally complete and publishable exactly when it is a JSON object with a top-level `games` list and every list entry has a syntactically valid Chess.com game UUID that is unique within that response. “Incomplete” means failure of one of those requirements—no additional completeness heuristic is permitted. In particular, do not require a nonempty list, an expected row count, complete participant metadata, or valid PGN, and do not compare remote omissions with a local count. A valid empty list is publishable, omissions are handled by merge, and all other record defects remain raw for import-time handling. A structurally incomplete, failed, or interrupted publication leaves the prior month file unchanged or the missing target absent. The current month merges by UUID: add new games, replace corrected representations, and retain locally known games omitted by the response. One eligible month request failure does not stop other eligible months; successful month publications remain and acquisition finishes `1`.
- **Normalization:** Accept only `rules = chess` games from the normal starting board with exactly one participant UUID matching the effective trainer UUID. Preserve exact source PGN and map only the authority-defined trainer-oriented columns: source URL; trainer color and UUID; nullable opponent UUID and ratings; nullable start/end UTC timestamps; nullable trainer outcome and termination reason; nullable source time control and time class. Chess.com's numeric end time takes precedence over disagreeing PGN metadata. All normalized timestamps use canonical `YYYY-MM-DDTHH:MM:SSZ` UTC text. Non-standard, trainer-absent, malformed, or illegal games remain raw, produce a warning, and create no new normalized rows.
- **Replay and persistence:** A valid N-move game yields exactly N+1 zero-based occurrences. Each occurrence stores the outgoing UCI move and its halfmove/fullmove counters; only the final occurrence has `NULL` outgoing move. Repeated positions resolve to the same permanent canonical DB-02 identity. Fully validate and normalize a game before write work. Then, in one transaction for that game, insert or update its metadata, replace its complete occurrence set when correcting, and create/reuse all positions. Each valid game commits independently; later invalid input or interruption preserves earlier commits. A valid accepted correction performs full replacement only after validation; a malformed or illegal correction preserves prior metadata and occurrences.
- **Opaque transaction composition:** The game persistence service must be able to write the game row, canonical positions, and all occurrences through one package-owned transaction while callers see only operation-specific methods and ordinary values. It must not expose SQLAlchemy `Connection`, `sqlite3.Connection`, `raw_connection`, or general SQL execution as a public contract. Prefer package-internal composition over changing DB-02's public position API. If the existing position unit of work cannot be safely composed, a narrowly bounded connection/position-package adjustment is permitted solely to bind the position resolver and game writer to the same internal transaction; prove rollback and continued handle opacity.
- **Excluded:** Schema/DDL changes; new dependencies; migrations or old rows; creating or modifying `archives/<username>.json`; rewriting existing historical month files; raw deletion; profile fetching; alternate/publicly configurable API endpoints; ETags; fetch-state, player, corpus, fingerprint, accepted-state, manifest, run, history, source-version, or failure tables; broad transactions across multiple games; non-atomic raw writes; entering-move occurrence semantics; legacy imports, wrappers, delegation, copying, patching, commands, tests, or compatibility. Also excluded are production `backend/app`, frontend, openings, analysis, the old database, application integration, migration, cutover, retirement, existing historical raw-file edits, and legacy-tool/test edits.
- **Deferred case:** Do not design or test special behavior for a correction that changes a previously accepted game into non-standard or trainer-absent input. Ordinary non-standard/trainer-absent skip fixtures must not model a prior accepted row with the same UUID. Escalate if real source or proof reveals that transition.
