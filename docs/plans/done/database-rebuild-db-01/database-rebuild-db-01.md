# DB-01 database schema substrate - create and inspect the exact empty SQLite database

> **Status:** done - all three stages and the complete focused proof are accepted

- **Read trigger:** Read before any DB-01 implementation or proof work.
- **Upstream:** `docs/master-plans/database-rebuild/database-rebuild.md` for the clean-rewrite sequence and DB-01 envelope; `docs/grilling-docs/database-rebuild-direction.md` and `docs/grilling-docs/database-rebuild-schema.md` as the only binding product, data, and schema authorities; `docs/grilling-docs/database-rebuild-db-01.md` as the confirmed, subordinate implementation handoff.

## Outcome

A supported package can safely create and reopen an empty neighboring SQLite database containing exactly the approved ten tables, their exact declared constraints, and `PRAGMA user_version = 1`. Thin commands create the database, generically inspect any readable SQLite database, and publish a deterministic production-facing Markdown schema reference without changing the legacy database or schema reference.

## Scope

- **Included:** The permanent `chess_move_trainer.database` package; synchronous SQLAlchemy Core connection and transaction ownership with bounded direct SQLite operations; one versioned SQL resource as the sole executable DDL definition; safe and idempotent v1 creation; single-sourced strict compatibility comparison; generic read-only inspection; the confirmed Typer command/help/output/exit contract; deterministic atomic Markdown publication; focused schema, CLI, package-boundary, and generated-reference proof.
- **Expected areas:** `src/chess_move_trainer/__init__.py`, `src/chess_move_trainer/database/**`, `tests/database/**`, `pyproject.toml` only for discovery/import and SQL-resource packaging of the new `src` namespace while preserving existing package discovery, the new root `setup-tools.ps1`, `data/database/schema.md`, and `docs/README.md` for a separate generated-reference link. The existing dependency pins in `requirements.txt` are an accepted prerequisite and are not implementation work.
- **Excluded:** Feeders and application readers beyond generic inspection; canonical chess logic; populated rows; secondary access-path indexes; APIs, production `backend/app`, frontend, and E2E; ORM, async database access, generic repository machinery, and framework types in public service contracts; migration, repair, overwrite, force, production default paths, environment fallback, WAL/journal policy, cutover, old-database changes or deletion; extra schema/history/state/run tables or authorizer machinery; legacy implementation reuse; broad maintenance checks. `setup.ps1`, every other existing script, legacy-schema test `tests/database/test_schema.py`, `data/database/schema.txt`, `requirements.txt`, the master plan, binding authorities, and confirmed handoff remain untouched.
